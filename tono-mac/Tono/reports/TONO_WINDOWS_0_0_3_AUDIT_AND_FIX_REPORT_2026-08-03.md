# Tono Windows 0.0.3 — 五轮审计与修复完整报告

**日期:** 2026-08-03
**版本:** 0.0.3（Windows 测试线）
**取代:** 0.0.2 / 0.0.1 / Test 2–6（全部停用）
**目的:** 在真机测试之前，把静态可发现的问题清干净，并诚实交代哪些**只有真机能证明**。

## 0. 给测试者的一页纸

### 装之前

0.0.3 相对 0.0.2 是正常升级，直接装即可。**装完第一件事：确认左下角显示 `v0.0.3`。**

### 出问题时的三条退路（按顺序）

1. **界面里点「断开连接」。** 已确认可用：应用与服务走的是 Windows 命名管道（本地进程通信，不经过 TCP/IP），而防火墙规则只作用在网络连接层，持久化的兜底规则明确放行环回——**即使全网被拦死，这个按钮照样能用**。
2. **开始菜单 →「Tono — 恢复网络 (Restore Network)」**，点一下弹 UAC，解除全部拦截。这是这一版新加的。
3. 管理员 PowerShell：
   ```powershell
   taskkill /F /IM Tono.exe
   sc stop TonoService
   & "C:\ProgramData\Tono\bin\tono-service.exe" --emergency-disarm
   ```
   看到「网络保护已解除」即恢复。

**重启电脑救不了网络**——拦截规则是持久化、开机自恢复的，这是"断线绝不漏流量"的设计。必须用上面三条之一。

### 现在有日志了

之前所有版本，服务端日志**全部丢失**——它只往 stdout 写，而 Windows 服务根本没有 stdout。这是我们对客户机器完全瞎的原因。0.0.3 起写到：

```
C:\ProgramData\Tono\logs\tono-service.log     ← 服务端（新增，最关键）
%APPDATA%\com.raydocs.tono\logs\latest.log    ← 应用端
```

出任何问题，**两个都要**。另外界面上的「Copy details」按钮会把诊断信息复制到剪贴板。

### 测试时重点盯这几处

| 场景 | 该看到什么 | 曾经的故障 |
|---|---|---|
| 连接卡在「Enabling WFP Kill Switch」 | 最多约 25 秒出明确报错（BFE 未运行 / 防火墙引擎无响应），不是无限等待 | 永久卡死，窗口无响应，关不掉 |
| 睡眠唤醒 / 切换 Wi-Fi | 直接重连，不再先报一次「DNS 端口不可用」 | 每次必先失败一次 |
| 点断开后等几秒 | 保持断开 | 后台任务可能把防火墙又装回去 |
| 开机后立即打开 Tono | 状态真实（未知就说未知） | 显示「未连接」但实际全网被拦 |
| 装了 WSL / Hyper-V 的机器 | DNS 保护正常 | 伪网卡永久毒化状态 + 每 2 秒一次 PowerShell 风暴 |
| 关闭窗口 / 退出 | 窗口立即响应；退出被拒时窗口重新出现并说明原因 | 消息泵死亡，进程退不出 |

## 1. 这一轮做了什么

七个独立视角的审计，加一个 21 agent 的逐模块逻辑通读：

| 轮次 | 视角 | 关键产出 |
|---|---|---|
| 1 | 连接流程 / IPC / WFP-DNS / 进程生命周期 / 前端 / 性能 | 12 条确认，已在 Test 6 修复 |
| 2 | 阻塞与无界等待 | 启动无窗口、连接流程唯一漏掉的超时、服务端 DNS 全模块无时限 |
| 3 | 降级路径（"别的东西已经坏掉之后"） | 产品对用户撒谎的三条路径 |
| 4 | Windows 专属未测代码 | DNS 的 IPv4/IPv6 混用、伪网卡毒化、安装器中止后不可卸载 |
| 5 | 流量泄漏端到端 | 规则集逐条枚举 + 16 条已验证正确的证据 |
| 6 | 本地安全面 | 提权到 SYSTEM 的完整利用链 |
| 7 | 跨进程竞态 | 可证明的永久死锁、断开被撤销、DNS 双写入者 |
| 8 | 文档/注释一致性 | 注释声称但代码不提供的保证 |
| 9 | 逐模块逻辑通读（10 模块 × 对抗验证） | 11 条确认、15 条驳回 |

**为什么越挖越多**：这个产品的正确性几乎全部依赖 Windows 专属、且"别的东西已经坏掉之后"才会走到的代码路径。这些路径在 macOS 上既跑不了也测不到，所以每换一个视角就能翻出一批新的。这不是代码质量差，是**测试可达性**的结构问题。

## 2. 修掉的问题（按后果分类）

### 2.1 永久变砖

- **`stop_core` 自死锁**（`manager.rs`）。tokio 的锁不可重入，而代码在持有锁的作用域内又去获取同一把锁。触发条件仅仅是"内核 3 秒内没被杀掉"（WinTUN 驱动拆卸时的已知情况）。一旦触发，服务端两把最外层的锁被永久占死，**所有变更操作全部堵死——包括解除防火墙**。用户点断开会超时，重试永远排在死锁后面。**不需要任何竞态，单进程必然触发。** 修法是彻底去掉第二次加锁而非挪位置；同时把全文件 20 多处可能重入的锁点逐个核查并把两处"当前安全但一次改写就会复现"的写法做成结构上不可能出错。
- **开机时 WFP 看门狗必崩**（`windows_kill_switch.rs`）。`Instant::now() - 3600秒` 在开机时下溢 panic，任务起来就死。后果是防火墙状态 1.5 秒后即报告"未生效"，应用判定不健康，**每 4 秒拆一次重连一次，无限循环**。
- **状态文件损坏永久拒绝服务**。所有权记录、DNS 快照、防火墙意图任一损坏，释放和连接都被永久拒绝，重启一样。现在改为隔离（重命名保留证据）并从实况证明恢复，绝不静默删除。
- **文档承诺的降级出口不存在**。设计文档写明「CIM 连续失败三轮后接受注册表证明的恢复，以免用户被永久困在保护离线」，代码里那个计数器只被拼进错误字符串、从未与任何阈值比较。在 PowerShell 受限、AppLocker、WMI 损坏的机器上，**断开/登出/退出全部永久被拒**。已按文档实现：需要注册表精确回读匹配 + 持续失败计数，且始终在状态里出现。

### 2.2 产品对用户撒谎

- **开机探测把任何通信失败当成"确认已解除"**。服务开机时先做恢复和对账、**之后才开始监听通信**，那几秒管道不存在，应用却已经在探测。后果连成一条链：界面显示"未连接、无保护"而防火墙实际在拦（所以没网）→ 点断开，代码看到"既没连接也没被拦"直接**返回成功**什么也不做 → 点退出，判定"没有保护需要释放"**放行退出**，把拦截留在机器上没有任何程序管它。现在改为三态，未知就明说未知，且未知时保留可释放路径。
- **用户点了断开，防火墙又自己装回去**。策略同步任务不受断开操作的中止范围管辖，而它调用的重连辅助函数完全没有代际检查。用户在"保护离线"闪烁的一两秒里点断开——那恰恰是用户最可能点的时机——释放完成、界面显示已断开，然后那个后台任务继续跑完，把防火墙重新装上、内核重启、DNS 重新指向环回。**没有用户操作，也没有审计记录。**
- **保持拦截的清理路径却跑了释放决策表**。对"已装防火墙但尚未验证"的连接，决策表解析为完全释放，清掉标记而服务端仍在拦截 → 界面显示未连接、退出时跳过释放。三处站点已统一。

### 2.3 泄漏与提权

- **提权到 SYSTEM 的完整链条**（两次 IPC 调用，可持久化）。客户端声明的资产可以命名为 `.exe`，被服务以 SYSTEM 身份复制进一个**内核路径白名单接受的目录**，第二次调用即以 SYSTEM 执行，且开机自动重放，还继承了防火墙里那个按程序开的唯一放行口子。三处同时封堵：暂存目录不再是允许的内核位置、可执行扩展名一律拒绝（含 `payload.exe.` 尾点和 NTFS 数据流走私）、内核启动前必须匹配固定的 SHA-256。
- **身份可伪造**：认证只看客户端提供的路径上的文件系统证据，而防护函数**写好了却从未被调用**（全仓库零调用方）。现已接上，并要求本地驱动器 + 规范化后复查；更进一步见 §3。
- **"停止内核"缺失字段默认解除防火墙**——对 fail-closed 产品这个方向就是错的，改为缺失即保持拦截。
- **DIRECT 放行在没有隧道的状态下依然对全机所有进程敞开**（最多 256 个口子），已限定为仅锁定态。
- **隧道放行规则可能比它服务的内核活得久**：那条规则没有协议、端口、程序任何限制，内核重启后网卡标识可能已被系统回收给物理网卡。现绑定到内核实例（进程 ID + 重启计数），对不上就不渲染。
- **服务端会解析客户端给的主机名并把结果变成放行规则**——系统解析器被投毒即可让攻击者选定放行目标。现只接受字面 IP。

### 2.4 Windows 专属正确性

- **DNS 把 IPv6 地址塞进只认 IPv4 的接口**。两种可能结果都是灾难：要么每块网卡都失败→全机连不上；要么静默丢弃 `::1`→**IPv6 DNS 泄漏而界面显示已保护**。现按协议族分开施加并分别回读验证。
- **WSL / Hyper-V / 蓝牙 PAN 等伪网卡永久毒化状态**，并驱动每 2 秒一次的 PowerShell 风暴。现按"该机制能否真正配置"选择网卡，且看门狗有退避与失败上限。
- **安装器可能在服务已注册运行、但卸载器和控制面板条目尚未写入时中止** → 装不上也卸不掉。已重排顺序并加失败回滚。
- **服务端不写日志**（见 §0）。

### 2.5 界面与可用性

界面塌陷（布局样式在客户机器上未生效）已做两层加固：改为构建期 CSS 文件，并把结构性布局属性同时内联——**即使 CSS 一个字节都没加载，界面也不会塌**。侧栏常驻版本号。没选节点时点连接自动跳转节点页，错误移到按钮正下方。退出流程不再阻塞 UI 线程；退出被拒时窗口重新出现并说明原因。

## 3. 这一版的结构性改动：IPC 库收进自建仓库

原先依赖第三方仓库的**移动分支**（`branch = "dev"`），上游随时可以改动我们脚下的地基，而且两个真实缺陷在原地无法修复。现已 vendor 到 `tono-win/vendor/kode-bridge`，所有本地改动带 `// Tono:` 标记以便将来同步上游。

**对端身份验证**：接受连接时取客户端进程 ID，打开其令牌读出用户 SID，要求等于声明的身份，然后才信任原有证据。五种情形一张判定表，**只有一个分支返回通过**——无法命名、打不开、令牌读不到、身份不符，全部拒绝。理由是：一个说不出调用方是谁的服务，无法区分"没查出来"和"就是别人"。

买到了什么，说准确：它**挡不住接管**（那是保留的产品设计），但让**被盗令牌离开所有者账户即一文不值**——泄漏途径包括备份、崩溃转储、误配的文件夹权限。挡不住的是已经跑在所有者会话里的东西（被攻陷的应用进程、DLL 注入）——这道门验的是账户，不是程序。

**同步连接根治**：管道打开与服务端验证原先同步执行在异步路径内，导致**所有客户端超时形同虚设**，且一个卡死的服务会占死整个通信运行时。已移至阻塞线程池，并加信号量上限（被取消的阻塞任务会留下游离线程直到系统调用返回——这是固有代价，不能假装不存在）。A/B 实测：旧写法 50ms 超时在 300ms 后才返回**成功**；新写法 50ms 内正常触发。

**管道权限收紧**：从"所有已认证用户"改为**仅交互式登录**，并显式拒绝网络登录（拒绝项排在允许项之前）。域环境里原先任何一台机器都能通过 `\\主机名\pipe\tono-service` 够到 LocalSystem 服务。

> 应用侧那层"整个请求丢到阻塞池"的绕行代码**特意保留**。根治已在 vendor 里完成，但两处同时改，万一真机出回归就无法归因。等真机验证通过后再单独拆除。

## 4. 测试的可信度（诚实交代）

一轮审计对测试套件本身做了统计：**约 66% 的测试在 CI 实际运行的平台上真正验证了行为**。其余是 Windows 专属不编译、跑在"永远成功的桩"之上、或断言常量。

最要紧的一条：**`wfp.rs`（965 行 unsafe FFI）在任何测试配置下都不编译**，off-Windows 的引擎桩无条件返回成功——也就是说整个状态机是在"防火墙引擎从不出错"的假设下被验证的。

这一版加了两处测试接缝，让原本结构上不可达的 fail-closed 分支变得可测：

1. **"是否还在环回 DNS"** 的探测在测试里永远返回 false，导致损坏快照的拒绝分支无法覆盖。
2. **"内核终止未确认"** 在 macOS 上无法用真实进程构造（SIGKILL 必达，且实测确认 tokio 对已回收子进程返回 Ok——原 agent 的假设是错的）。

这两处正是规范审计那句话的实例：**永远不会失败的测试比没有测试更糟，因为它被当成了覆盖率。**

## 5. 只有真机能证明的事

静态审计到此为止。以下按重要性排序，**测试时请优先验证**：

### 必须验证（关系到能否发布）

1. **内核完整性校验的接线**。本版新增"内核 SHA-256 必须匹配才启动"。构建脚本用本次实际打包的内核计算摘要并编译期注入。若接线有误，表现是**连接直接失败并提示内核校验不通过**——这是 fail-closed 的正确方向，但产品不可用。**这是第一个要确认的。**
2. **升级路径**：从 0.0.2 覆盖安装到 0.0.3，服务能否被正确替换。
3. **对端身份验证不误伤真实用户**：服务能否 `OpenProcess` 到每一个合法客户端；UAC 分割令牌下提权与非提权的 SID 是否一致。
4. **管道权限收紧不误伤**：交互式登录是否覆盖所有正常使用场景。

### 重点观察

5. 25 秒防火墙超时、40 秒 DNS 恢复超时在真实慢机 / 装了杀软的机器上是否会误报（方向是失败即拦截，属于安全侧误报）。
6. 新的 DNS 施加方式（IPv4 走 CIM、IPv6 走 netsh）在各种网卡上的真实行为，以及回读验证是否产生误判。
7. `TerminateProcess` 后 SCM 是否及时报告已停止；抑制自动重启是否真的生效。
8. 强制停止卡死服务的升级路径在真实场景下是否奏效。

### 已知无法从静态分析回答（泄漏相关）

9. **虚拟交换机绕过**：WSL2 / Docker Desktop / Hyper-V 虚拟机的流量在 NDIS 层桥接，不经过主机的 WFP 连接层。**这类环境很可能完全绕过隧道。** 验证：连接状态下执行 `wsl -e curl -s -m 5 https://ifconfig.me`，若返回真实公网 IP 即为泄漏。
10. **入站已建立连接的出站数据**：只在连接层拦截，机器上任何监听服务接受外来连接后回送的数据不受管辖。
11. **建连前的既有连接**不会被重置——上防火墙那一刻已存在的连接会继续跑。
12. 第三方安全软件若使用 WFP 的否决标志，可以压过我们的拦截（我们没有使用该标志）。

> 9–12 属于设计层面的取舍，不是这轮引入的缺陷。列出来是因为它们直接关系到产品对外能承诺什么。建议真机测试时至少跑一次第 9 条——**如果客户机器上装了 WSL 或 Docker，这是最可能的实际泄漏来源**。

## 6. 保留的产品决策

**多用户机器上任何本地用户可接管防火墙所有权。** 审计报为高危，查证后确认是**现有产品设计**——仓库里有测试明确断言该行为，且这个无条件接管正是被顶掉的用户能靠重连自救的机制；禁止覆盖反而会造出新的变砖场景。已确认保持现状。
