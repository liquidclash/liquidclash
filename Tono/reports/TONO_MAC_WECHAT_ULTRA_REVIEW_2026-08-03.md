# Tono macOS Build 37 微信直连与全面审查报告 (ultracode)

日期: 2026-08-03  |  对象: liquidclash/Tono (macOS, 0.0.1-build37)  |  方法: 6 维并行深审 + 逐项对抗验证 (12 agents, 44 项确认 / 8 项驳回)


用户症状: 隧道连接后，原生微信发送/接收图片一直转圈；文字消息基本可用。


## 一、微信直连路由（发图转圈根因）

**维度综述**: Root cause of "WeChat images spin forever": the native-trial direct route has never actually routed any WeChat TCP flow direct, and the traffic that matters for images cannot even be attributed to WeChat. Two independent P0s: (1) Rule semantics — every emitted TCP rule (ConfigPipeline.swift:577, :592) ANDs (DOMAIN,host) with (IP-CIDR,pin/32,no-resolve) under fake-ip DNS. In Mihomo, whenever the destination is a fake IP or a hosts-pinned IP with a live reverse mapping, preHandleMetadata sets Host and CLEARS DstIP; with no-resolve the IP-CIDR sub-rule then never matches (and never triggers resolution). Conversely, when WeChat connects to an IP literal from its own HTTPDNS (its normal image-CDN pattern) or after the 10s hosts reverse-mapping expires, DstIP is valid but Host is empty, so the DOMAIN sub-rule fails. Every branch fails → all WeChat TCP traffic falls to MATCH,Tono-Exit. (2) Process coverage — managedDirectProcessPaths (ConfigPipeline.swift:90) pins only /Applications/WeChat.app/Contents/MacOS/WeChat, but WeChat 4.x does image/CDN transfer in helper executables (WeChatAppEx network-service helper etc.), which can never match the exact PROCESS-PATH. Why text works while images spin: text rides the main binary's persistent long connection (long.weixin.qq.com MMTLS), which tolerates being proxied through the US exit; images use fresh CDN connections from helper processes to geo-scheduled Tencent edges — those flows are proxied (not PF-blocked, so they hang rather than fail fast) through the US exit to China-region CDN edges, and the hosts:/pin layer amplifies the stall because pins are resolved once at connect through the exit's US DoH (AppState.swift:2742 + ConfigPipeline.swift:200-203), yielding wrong-region /32s that also feed the PF direct allowlist. Supporting P1s: exit-resolved geo-DNS pins, exact-DOMAIN-only matching with no DOMAIN-SUFFIX or SNI sniffing (IP-literal flows are unclassifiable), and one-shot stale /32 pinning with silent per-domain drop. P2: UDP media rules share the process-path gap. Fix order: drop the IP-CIDR sub-rule from the TCP AND rules (hosts pin + PF endpoint allowlist already bound the dial), widen process matching to the WeChat.app bundle (PROCESS-PATH-REGEX), resolve pins region-correctly and refresh them, and add suffix/sniffer coverage for CDN subdomains and IP-literal flows.


### [P0] AND(DOMAIN + IP-CIDR/32,no-resolve) is unsatisfiable under fake-ip; every Tono-China-Direct TCP rule is dead code

- 位置: `Tono/Core/ConfigPipeline.swift:577`

- 问题: The emitted rule `AND,((NETWORK,TCP),(DST-PORT,p),(DOMAIN,host),(IP-CIDR,addr/32,no-resolve),(PROCESS-PATH,path)),Tono-China-Direct` requires metadata.Host == host AND metadata.DstIP == addr simultaneously. Under the config this pipeline generates (tonoDNS lines 189-203: enhanced-mode fake-ip; hosts: block lines 534-543 with use-hosts:true), Mihomo's preHandleMetadata makes that impossible in every branch: (1) if the client connected to a fake IP (198.18.0.0/16), Mihomo sets Host from the fake pool and CLEARS DstIP to the invalid addr — the IP-CIDR sub-rule with no-resolve returns false on an invalid DstIP and, because no-resolve makes ShouldResolveIP()==false, DstIP is never populated, so the AND short-circuits false; (2) if the client connected to the pinned real IP (hosts answers win over fake-ip in Mihomo's DNS middleware chain), Mihomo's withHosts middleware inserted a ~10s IP→host reverse mapping, FindHostByIP hits it, and because FakeIPEnabled() is true DstIP is again cleared — IP-CIDR fails; (3) if the mapping expired or WeChat connected to an IP literal obtained from its own HTTPDNS (its normal CDN pattern), DstIP is valid but Host is empty (no sniffer: configured), so the DOMAIN sub-rule fails first. The identical construction at line 592 kills all webDomainPins rules too. Result: 100% of WeChat TCP traffic (and all 'web direct' traffic) falls through to `MATCH,Tono-Exit` (line 600) and is proxied through the US exit — the entire native-trial direct feature has never routed a single TCP connection direct.

- 触发场景: User connects the tunnel, cloud policy contains e.g. shmmsns.qpic.cn with a pinned IP. WeChat resolves it (gets pinned real IP from hosts:, or a fake IP), opens TCP 443. Mihomo clears DstIP during fake-ip/hosts preprocessing, IP-CIDR,no-resolve never matches, connection routes to Tono-Exit. Image upload/download goes via US exit to a Tencent China CDN edge and stalls; the WeChat spinner never completes.

- 修复建议: Drop the (IP-CIDR,addr/32,no-resolve) sub-rule from the TCP AND rules (lines 577 and 592). Constrain the dialed address instead via the existing hosts: pin (use-hosts:true makes the DIRECT outbound resolve to exactly the pinned addresses) plus the PF sessionDirectEndpoints allowlist which already bounds physical egress to those exact IP:port tuples. Emit `AND,((NETWORK,TCP),(DST-PORT,p),(DOMAIN,host),(PROCESS-PATH,path)),Tono-China-Direct`. Add a regression test that generates the runtime YAML and asserts against a live mihomo `-t`/rule-match check that a fake-ip-mode connection with Host=pin.host actually selects Tono-China-Direct.

- 验证结论: ConfigPipeline.swift:577 and :592 emit AND rules requiring both DOMAIN and IP-CIDR/32(no-resolve); the runtime config (tonoDNS at :189-203, used at :544) is enhanced-mode fake-ip with use-hosts:true, hosts: pins at :534-543, and no sniffer block anywhere. Under Mihomo semantics all three branches fail as claimed: (1) fake-IP dst -> preHandleMetadata sets Host and clears DstIP (FakeIPEnabled), and no-resolve keeps the AND rule's ShouldResolveIP false so IP-CIDR sees an invalid DstIP and fails; (2) real pinned-IP dst within the withHosts middleware's ~10s IP->host mapping window -> FindHostByIP hits, DstIP again cleared, IP-CIDR fails; (3) IP-literal/expired-mapping dst -> Host empty, DOMAIN fails. All traffic falls to MATCH,Tono-Exit at :600. The feature is entirely dead code; P0 is correct.


### [P0] PROCESS-PATH pins only the main WeChat binary; WeChat 4.x image/CDN traffic comes from helper processes and can never match

- 位置: `Tono/Core/ConfigPipeline.swift:90`

- 问题: managedDirectProcessPaths (lines 90-92) contains only "/Applications/WeChat.app/Contents/MacOS/WeChat". On WeChat 4.x for macOS, image/media/CDN networking is performed by separate executables: WeChatAppEx.app/Contents/MacOS/WeChatAppEx, the dedicated network-service helper (WeChatAppEx Helper.app with --utility-sub-type=network.mojom.NetworkService), WeChatAppEx Helper (Renderer), WeChatHelper, wxplayer, wxocr — all with different exact executable paths (confirmed by live process listing). Mihomo PROCESS-PATH is an exact string match, so even after fixing the dead AND rule (finding 1), every image transfer initiated by a helper process fails the PROCESS-PATH sub-rule (lines 577, 582) and is proxied. The telemetry that would reveal this is itself blind: LocalTrafficAudit.isNativeWeChatProcess (Tono/Services/LocalTrafficAudit.swift:603-607) compares against the same single path, so helper-process connections are not even counted as WeChat traffic (weChatConnectionCount undercounts; weChatManagedDirectConnectionCount reads plausible).

- 触发场景: User sends a photo. The upload runs in the WeChatAppEx network-service helper whose PROCESS-PATH is .../WeChatAppEx Helper.app/... — the sub-rule (PROCESS-PATH,/Applications/WeChat.app/Contents/MacOS/WeChat) evaluates false, the AND rule fails, the flow routes to Tono-Exit and stalls. Text messages sent by the main binary's long connection still work through the proxy, matching the reported symptom exactly.

- 修复建议: Either enumerate the full helper set in managedDirectProcessPaths (WeChatAppEx, WeChatAppEx Helper variants, WeChatHelper, wxplayer, wxocr) or switch the emitted sub-rule to Mihomo's PROCESS-PATH-REGEX, e.g. `(PROCESS-PATH-REGEX,^/Applications/WeChat\.app/)`, which covers all bundle-internal executables while staying bounded to the reviewed app bundle. Update LocalTrafficAudit.isNativeWeChatProcess to prefix-match /Applications/WeChat.app/ so the WeChat trial counters reflect helper traffic.

- 验证结论: ConfigPipeline.swift:90-92 contains exactly one path, and lines 573/577/582 attach (PROCESS-PATH,/Applications/WeChat.app/Contents/MacOS/WeChat) to every direct rule. Mihomo PROCESS-PATH is an exact case-insensitive full-path match, so the observed helper executables (WeChatAppEx, its NetworkService helper, WeChatHelper, wxplayer, wxocr) can never satisfy it. LocalTrafficAudit.swift:603-607 confirmed: isNativeWeChatProcess exact-compares against managedDirectProcessPaths[0], so helper traffic is invisible to the WeChat counters. Independent second blocker that keeps image transfers broken even after fixing finding 1; matches the reported symptom (main-binary long connection works via proxy, helper-process image transfers stall). P0 stands.


### [P1] Direct-domain pins are resolved through the US exit's DoH, so the 'China direct' IPs are US-geolocated CDN edges

- 位置: `Tono/Services/AppState.swift:2742`

- 问题: resolveManagedDirectDomainPins (AppState.swift:2732-2771) resolves each policy host via api.resolveIPv4 → mihomo /dns/query (ClashAPI.swift:78-108). The runtime's only nameservers are https://1.1.1.1/dns-query#Tono-Exit and https://8.8.8.8/dns-query#Tono-Exit (ConfigPipeline.swift:200-203), i.e. queries egress from the US exit. Tencent CDN hostnames (qpic.cn, qlogo.cn, tc.qq.com, ...) are geo-DNS: the answers are edges chosen for the exit's location, not the user's China ISP. Those wrong-region IPs then become (a) the hosts: pins served to WeChat (ConfigPipeline.swift:534-543), (b) the /32s in the direct rules, and (c) the PF sessionDirectEndpoints allowlist (AppState.swift:1193-1200). Even with findings 1-2 fixed, 'direct' WeChat image traffic would connect from a China ISP straight to overseas/US CDN edges — slow or unreachable — defeating the point of the native trial route.

- 触发场景: Policy pins shmmsns.qpic.cn. Resolution through Tono-Exit (US) returns a Tencent edge serving North America. WeChat in China is handed that IP via hosts:, dials it 'direct' over the China ISP; cross-border RTT/loss to an edge not meant for that region makes image loads crawl or time out.

- 修复建议: Resolve managed direct pins over the physical interface with a China-appropriate resolver (e.g. DoH to 223.5.5.5 / 119.29.29.29, dialed via the Tono-China-Direct interface-bound path and permitted by a narrow PF exception during the resolution window), or have the cloud policy ship server-side region-resolved pinned addresses instead of client-side resolution through the exit.

- 验证结论: AppState.swift:2742 resolves via ClashAPI.resolveIPv4 (ClashAPI.swift:78-108, controller /dns/query), which uses the runtime resolver whose only nameservers are https://1.1.1.1 and https://8.8.8.8 DoH tagged #Tono-Exit (ConfigPipeline.swift:197-202), so queries egress from the US exit with no client-region ECS. Tencent CDN geo-DNS will return exit-region edges, and those addresses become the hosts: pins (:534-543), the /32 rule constraints, and the PF sessionDirectEndpoints allowlist (AppState.swift:1193-1200). Even with findings 1-2 fixed, 'direct' connections from a China ISP would target wrong-region edges. Not a total feature kill on its own (some hosts are not geo-sensitive, connections may work degraded), so P1 is the right severity.


### [P1] Exact DOMAIN matching cannot cover WeChat CDN subdomain fan-out or HTTPDNS IP-literal connections

- 位置: `Tono/Core/ConfigPipeline.swift:577`

- 问题: The pipeline can only express exact-host DOMAIN sub-rules (rule emission line 577; TonoTrafficPolicyDomain in Tono/Models/TonoAPIModels.swift:139-142 is host+ports; validatedManagedDirectDomain at ConfigPipeline.swift:807-820 validates single hosts against allowed suffixes but there is no DOMAIN-SUFFIX emission anywhere). WeChat image/media CDN uses a wide rotating subdomain set (shmmsns.qpic.cn, mmsns.qpic.cn, mmbiz.qpic.cn, vweixinthumb.tc.qq.com, wxapp.tc.qq.com, szshort/long.weixin.qq.com, dns.weixin.qq.com, ...); any subdomain absent from the cloud list silently proxies. Worse, WeChat's own HTTPDNS (dns.weixin.qq.com) hands the client raw CDN IPs and the helper connects by IP literal — metadata.Host is empty (no sniffer: block in the generated config), so NO domain-based rule can ever classify the flows that actually carry image bytes.

- 触发场景: WeChat queries its HTTPDNS, gets 183.x.x.x for an image shard, and opens TCP 443 to that literal IP. Host is empty; every DOMAIN rule fails; the flow proxies through the US exit and stalls. Alternatively a new mmsns shard subdomain appears that the cloud list lacks — same outcome.

- 修复建议: Add DOMAIN-SUFFIX support to the policy schema/pipeline for the already-reviewed suffix allowlist (qpic.cn, qlogo.cn, tc.qq.com, weixin.qq.com, ...), enable the config `sniffer:` block (TLS SNI sniffing) so IP-literal HTTPS flows regain a Host for domain rules, and/or add process-guarded IP-CIDR rules for Tencent's published CDN ranges (real CIDRs, not /32 pins) as the backstop for non-SNI flows.

- 验证结论: Verified from code: the policy schema is exact host+ports (TonoAPIModels.swift:139-142), validatedManagedDirectDomain (ConfigPipeline.swift:807-820) validates single exact hosts against a suffix allowlist, and grep confirms no DOMAIN-SUFFIX emission anywhere in the pipeline and no sniffer: block in the generated YAML. So any subdomain absent from the cloud list proxies, and IP-literal HTTPS flows (WeChat HTTPDNS pattern) have empty metadata.Host and can never match any domain rule. The HTTPDNS behavior itself is external knowledge but well documented for WeChat; the structural inability to classify such flows is confirmed from the code. P1 appropriate: a coverage/robustness gap rather than the primary breakage.


### [P1] One-shot /32 pinning at connect time: no re-resolution, silent per-domain drop, permanent hosts pin with no fallback

- 位置: `Tono/Services/AppState.swift:2732`

- 问题: Domain pins are resolved exactly once, during the connect sequence (AppState.swift:1180-1227 → resolveManagedDirectDomains). There is no TTL-based or periodic re-resolution for the lifetime of the session. Tencent CDN answers rotate on short TTLs, so pins go stale within minutes: (a) the hosts: entry keeps serving the stale IP to WeChat indefinitely; if that edge is drained, connections just time out — no DNS-level fallback is possible because hosts overrides resolution; (b) any fresh IP WeChat learns out-of-band is outside the PF sessionDirectEndpoints allowlist (armed at AppState.swift:1193-1200), so post-fix drift means direct attempts would be PF-blocked, not merely proxied. Additionally, resolveManagedDirectDomainPins returns nil on any resolution failure (lines 2742-2744, 2754) and the domain is silently omitted from rules/hosts with no log, no retry, and no user-visible signal — a cold DoH path at connect reproducibly drops pins.

- 触发场景: Session connected for 2 hours; the pinned qpic.cn edge is rotated out by Tencent. WeChat keeps being told the dead IP via hosts:, TCP connects hang, images spin. Or: at connect the DoH resolver times out for one host (2s timeout in ClashAPI.resolveIPv4), that domain gets no rule at all for the whole session.

- 修复建议: Re-resolve pins on a timer honoring DNS TTL (or at least every few minutes), diff against committedDirectPolicy, and reuse the existing rewriteConfig + armKillSwitch + reloadConfig path (already implemented at AppState.swift:1189-1214) to roll the new pins without a full reconnect. Log/audit each dropped domain and retry failed resolutions with backoff instead of silently omitting them.

- 验证结论: Verified: resolveManagedDirectDomains has exactly one call site, in the connect sequence (AppState.swift:1183); grep shows no timer, TTL handling, or periodic re-resolution anywhere. resolveManagedDirectDomainPins silently returns nil per domain on resolution failure (try? at :2742-2744) or empty answers (:2754) with no log or retry, and ClashAPI.resolveIPv4 has a 2s timeout (ClashAPI.swift:92) over a cold cross-continent DoH path, making per-domain drops at connect realistic. The hosts: pin then overrides DNS for the whole session with no fallback, and any out-of-band fresh IP falls outside the exact PF sessionDirectEndpoints tuples (:1193-1200). initialDirectPolicy (:2668-2697) starts with empty pins, so a dropped domain gets no rule at all. P1 stands given hard-failure staleness plus reproducible silent drops.


### [P2] UDP media endpoint rules also require the main-binary PROCESS-PATH, so helper-process voice/video/QUIC media cannot go direct

- 位置: `Tono/Core/ConfigPipeline.swift:581`

- 问题: The UDP rules (lines 581-583) are emitted inside `for processPath in managedDirectProcessPaths` and carry the same single-binary PROCESS-PATH constraint as the TCP rules. WeChat real-time media and QUIC-style transfers from WeChatAppEx/helper processes fail the sub-rule and are proxied (UDP relayed through the exit or degraded to TCP fallback). Unlike the TCP rules these UDP rules are otherwise satisfiable (IP-literal dst, no DOMAIN sub-rule, DstIP stays valid because media IPs are not in hosts/fake-ip mappings), so the process-path gap is the sole blocker. Note also the loop shape duplicates every media rule once per configured process path if the path list grows.

- 触发场景: A WeChat voice call from the helper process sends UDP to a pinned media endpoint on 8000/443; PROCESS-PATH mismatch routes it to the exit, adding cross-border latency or breaking the call if the exit's UDP relay is poor.

- 修复建议: Apply the same process-coverage fix as the TCP rules (helper path enumeration or PROCESS-PATH-REGEX,^/Applications/WeChat\.app/), and hoist the mediaEndpoints loop out of the per-path loop, emitting one rule per endpoint with the regex sub-rule.

- 验证结论: Verified at ConfigPipeline.swift:581-583: the UDP rules are emitted inside the `for processPath in managedDirectProcessPaths` loop (:573) and carry (PROCESS-PATH,path). The claim that these rules are otherwise satisfiable is correct: media endpoints are cloud-supplied IP literals (initialDirectPolicy, AppState.swift:2676-2686) dialed by address, so DstIP stays valid (not fake-ip, not in the hosts mapping) and there is no DOMAIN sub-rule — process path is the sole blocker for helper-originated UDP. The per-path duplication observation is also correct from the loop shape. Which specific media flows run in helpers vs the main binary is not fully provable from code, so P2 (moderate, contingent on process attribution) is the right severity.


## 二、Kill Switch / PF / 特权 Helper

**维度综述**: Kill switch / PF / privileged-helper review of Tono (macOS). Architecture answers to the posed questions: YES, there is a PF allowlist that must be widened for WeChat direct exits — the helper renders one 'pass out quick inet proto <t> to <ip> port <p> user root' rule per sessionDirectEndpoint (scripts/core-helper/KillSwitchManager.swift:1233-1238), restricted to tcp 80/443 and udp 443/8000 (validateSessionDirectEndpoints:751-775); everything else Mihomo dials direct hits 'block drop out quick all' and is dropped silently (no RST), which manifests exactly as an app-level infinite spinner. The app keeps PF and Clash in sync at connect time (arm-before-rewrite ordering at AppState.swift:1165/1193 is correct, and Mihomo runs as root so the 'user root' constraint matches), but the sync is fragile in three ways: (1) session endpoints are deliberately never persisted, so every helper-side self-heal (status() !live rewrite, restoreAtLaunch, sleep barrier) reloads PF without the WeChat exceptions while Mihomo keeps its Tono-China-Direct rules — proxied traffic keeps working, only WeChat direct traffic is silently dropped, matching the reported symptom (P1); (2) the endpoint contract is validated all-or-nothing and swallowed with try? at AppState.swift:1097, so one out-of-contract tuple in the cloud policy silently disables the whole direct feature and all WeChat traffic gets proxied — a plausible build-37 root cause on this dimension (P1); (3) every arm runs a machine-wide `pfctl -F states`, hanging all established flows after node switches/config reloads (P2). Also found: an installIfNeeded artifact-version bypass that can wedge connects and silently fail open after reboot (P2), a 30s arm IPC timeout the helper can legitimately exceed causing stuck-connect loops at the '正在启动保护隧道' stages (P2), a SystemProxy snapshot overwrite that can leave macOS pointing at a dead loopback proxy (P2), a several-second connect window where Mihomo has UDP direct rules PF does not yet permit (P3), and busy-helper probes misreported as 'helper unavailable' during disconnect (P3). Note: the primary root cause of the WeChat spinner (PROCESS-PATH pinned only to the main WeChat binary while WeChatAppEx helper processes do the media networking) lives in ConfigPipeline rule generation, outside this dimension; on the PF side those helper-process flows are proxied through Tono-Exit and are not dropped by PF.


### [P2] Helper PF self-heal reloads rules without sessionDirectEndpoints while Mihomo keeps routing WeChat direct — Clash routes direct, PF silently drops (spinner)

- 位置: `scripts/core-helper/KillSwitchManager.swift:296`

- 问题: PF is the enforcement layer for the Tono-China-Direct exits: renderRules() (KillSwitchManager.swift:1233-1238) only passes 'pass out quick inet proto <t> to <addr> port <p> user root' for the exact sessionDirectEndpoints supplied in the *last arm request*, and session endpoints are deliberately never persisted (loadState() hardcodes sessionDirectEndpoints: [] at line 493; persistentObject() at 510-527 omits the key; self-test asserts persisted["sessionDirectEndpoints"] == nil at line 1792). But status() at lines 285-318 self-heals: whenever effectiveStatus() is false (pf disabled/anchor flushed by another product, macOS pf reload, prior pfctl error) it re-renders and reloads PF from the *persisted* state — i.e. WITHOUT the WeChat direct pass rules — and flushes all states, while leaving Mihomo running with the full Tono-China-Direct rule set. From then on every WeChat direct dial (root Mihomo → pinned IP:80/443 tcp, :443/8000 udp on en0) hits 'block drop out quick all' (line 1239) and is dropped with no RST, so WeChat spins forever while all proxied traffic (utun199 + proxyTargets, which ARE persisted) keeps working — exactly the reported symptom profile. status() is reachable mid-session: LiquidClashApp.swift:140 (launch refresh), KillSwitchService.swift:79 (after any arm IPC error/timeout the catch path calls killSwitchStatus(), so a single timed-out re-arm during node switch/config reload can trigger the heal), and KillSwitchService.disarm's probe (line 116). No signal is returned to the GUI that session exceptions were dropped, and nothing reconciles PF back with the running Clash config.

- 触发场景: User is connected with WeChat direct policy active. Another firewall product (or a pfctl invocation, or a transient re-arm timeout followed by the status probe) leaves the tono.killswitch anchor not-live. The next /killswitch/status call heals PF from disk: tunnel/proxy/control-plane rules return, session direct rules do not. Mihomo still classifies WeChat image traffic as Tono-China-Direct and dials the pinned IPs directly as root; PF silently drops every packet. WeChat image send/receive spins indefinitely; everything else works, so the user has no way to diagnose it short of a full reconnect.

- 修复建议: Make the heal path report degradation and make the GUI reconcile: (1) in status(), when the !live rewrite occurs, include e.g. "healed": true / "sessionExceptionsDropped": true in the response; (2) in KillSwitchService.refreshStatus()/arm catch path, on seeing that flag (or whenever armed&&live after a heal), trigger PrivilegedRuntimeCoordinator.armKillSwitch(... sessionDirectEndpoints: activeDirectPolicy?.sessionEndpoints ...) to re-install the exceptions. Alternatively persist sessionDirectEndpoints alongside a core-run nonce so a heal within the same core session restores them, still clearing them on boot/helper restart.

- 验证结论: Every cited mechanic is accurate: status() (KillSwitchManager.swift:285-318) re-renders and reloads PF from loadState() when effectiveStatus() is false, loadState() hardcodes sessionDirectEndpoints: [] (line 493), persistentObject() omits the key (510-527, asserted by the self-test at 1792), and renderRules emits the session pass rules only from in-memory state (1233-1238) ahead of 'block drop out quick all' (1239). A heal therefore removes the WeChat direct pass rules while the still-running Mihomo config keeps Tono-China-Direct rules, producing silent drops with no healed/degraded flag in the response (320-328) and no GUI reconciliation. Severity is downgraded from P1 to P2 because the trigger chain is narrow: it requires an external event making PF not-live mid-session (pfctl -d, third-party anchor flush) AND a mid-session status probe, which the GUI issues only on arm-IPC failure (KillSwitchService.swift:79), disarm (116), or app launch (LiquidClashApp.swift:140, when no session is active); and the divergence self-heals on the next node switch (AppState.swift:2068-2074) or config reload (2333-2341), both of which re-send activeDirectPolicy sessionEndpoints. Real defect, matching symptom profile, but a conditional secondary cause rather than the primary build-37 bug.


### [P3] Global `pfctl -F states` on every arm kills all established flows with silent drops afterwards

- 位置: `scripts/core-helper/KillSwitchManager.swift:1373`

- 问题: ensureAnchorLoaded(flushStates: true) is called on every arm (line 219), every status self-heal (298), restoreAtLaunch (335), emergency block (348), and sleep barrier (244). It runs `/sbin/pfctl -F states` — a machine-wide state flush, not scoped to the tono.killswitch anchor. Because the final rule is `block drop out quick all` (line 1239), mid-stream packets of previously established TCP connections no longer match any state and — since macOS PF pass rules implicitly require `flags S/SA` for TCP state creation — cannot re-create state either; they are dropped with no RST. Every mid-session re-arm (node switch AppState.swift:2068, reloadCoreConfig AppState.swift:2333, cloud policy re-arm 1193) therefore hangs every established connection on the machine (WeChat long-poll and media transfers included) until each app's own timeout, presenting as multi-second to multi-minute spinners even when the new allowlist is identical or a superset of the old one.

- 触发场景: User is mid-WeChat-image-upload when a rules edit triggers reloadCoreConfig, or they switch exit node. arm() re-renders identical session rules and flushes all PF states. The in-flight upload's TCP connection dies silently (no RST); WeChat waits on the dead socket and the transfer spins until WeChat's internal timeout, then may or may not retry.

- 修复建议: Only flush states when the new rule set actually revokes permissions, and flush selectively: compute the endpoints removed relative to the previous state and use `pfctl -k <host>` / `pfctl -k 0.0.0.0/0 -k <addr>` per revoked tuple (and flush per-interface for removed tunnels), instead of a global `-F states`. Keep the global flush only for the emergency/sleep barrier paths where revocation of everything is intended.

- 验证结论: The code claim is exact: ensureAnchorLoaded runs an unscoped '/sbin/pfctl -F states' (KillSwitchManager.swift:1373) and is called with flushStates: true from arm (219), the status heal (298), restoreAtLaunch (335), installEmergencyBlock (348), and the sleep barrier (244); mid-session re-arms do occur on node switch (AppState.swift:2068) and reloadCoreConfig (2333). The Mihomo/PF semantics are also right (macOS pf TCP pass rules default to flags S/SA, so flushed mid-stream flows cannot re-create state and hit 'block drop out quick all' silently). However the user-impact is overstated: both mid-session re-arm paths deliberately call api.closeAllConnections moments after the arm (AppState.swift:2081, 2364), so Mihomo-relayed flows — which is nearly all traffic in this always-TUN product — receive clean closes and apps retry promptly; UDP flows re-create state on the next packet; the incremental damage of the global flush is limited to non-Mihomo flows (tailscaled DERP, inbound sessions, loopback-external) and a few seconds of stall before the intentional close. Selective '-k'-based revocation is the right fix, but this is a moderate-polish disruption issue, not a P2 driver of the reported spinner.


### [P3] installIfNeeded artifact-version bypass can declare the helper ready without any live daemon (or with a stale older daemon), causing wedged connects and post-reboot fail-open

- 位置: `Tono/Core/HelperManager.swift:75`
